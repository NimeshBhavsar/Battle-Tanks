# Overall Architecture

> **Status:** this document started as the design plan and has been updated to describe
> the game **as built** (through commit `7b53e8e`, *v10 Statistics added at end of
> match*). Where the implementation differs from the original plan, the text below
> describes what the code does and [Deviations from the original plan](#deviations-from-the-original-plan)
> lists what changed. For a player-facing tour with screenshots see
> [docs/FEATURES.md](docs/FEATURES.md).

```
                   +--------------------------+
                   |        server.py         |
                   |--------------------------|
                   | Game Controller          |
                   | Turn Management          |
                   | Physics Authority        |
                   | Collision Detection      |
                   | Damage / Terrain / Fuel  |
                   | Match Statistics         |
                   +------------+-------------+
                                |
                  Local Network (TCP sockets, JSON)
              ------------------------------------
               |                                  |
               |                                  |
        +------+--------+                  +------+--------+
        | client.py     |                  | client.py     |
        |---------------|                  |---------------|
        | Render Game   |                  | Render Game   |
        | Read Inputs   |                  | Read Inputs   |
        | Visual Effects|                  | Visual Effects|
        | End-screen    |                  | End-screen    |
        |  chart        |                  |  chart        |
        +---------------+                  +---------------+
```

The server is the **single source of truth**.

Clients **never calculate game rules**. (They do run purely cosmetic effects such as
particles and screen shake, which never feed back into the game.)

Clients only

* draw
* send player input
* receive updated game state


Values as built

| ------ | ------ | ------ | ------------ |
| Light  | 1      | 30     | 20           |
| Medium | 3      | 40     | 35           |
| Heavy  | 6      | 70     | 40           |

(Original plan: Light 20 damage, Heavy radius 50 - both rebalanced during play-testing.)

Weight affects projectile motion (heavier shells fall faster) and the size of the shell
on screen, which is also its hit size.

# Turn Manager

Very simple. On a turn the player may aim freely and then does **one** of two things.

```
Player 1

↓

Move

or

Shoot

↓

End Turn

↓

Player 2

↓

Move

or

Shoot
```

Pseudo (as implemented in the server)

```
current_player

wait for action

if moved

    turn ends when the movement key is released

if fired

    simulate projectile

    explosion

    damage

    terrain

    if only one tank is left -> game over
    otherwise next turn (and possibly spawn a fuel can)
```

Firing is only allowed if the player has not moved that turn.

# Physics Engine

This is isolated: it knows nothing about tanks.

Input

```
Position

Angle

Power

Weight
```

Output

```
Projectile Position
```

Formula (as built - screen y grows downward, so "up" is negative)

```
speed = power * 0.25                      (px per frame)

vx =  speed * cos(angle)

vy = -speed * sin(angle)

gravity = 9.8 * (weight * 0.05)           (per frame)
```

Every frame

```
x += vx

y += vy

vy += gravity
```

The tank's `preview_trajectory()` reuses exactly the same step function, so the aiming
arc matches the real shot.

---

# Collision Engine

Checks

```
Projectile

↓

Tank?          (opponents only)

↓

Terrain?

↓

Out of map?
```

Returns

```
Explosion Point
```

A tank counts as hit if the shell touches its body rectangle **or a thin band around its
barrel**. Both have a 10 px forgiving margin (`TANK_HITBOX_PADDING`) plus the shell's own
radius.

---

# Damage Engine

Input

```
Explosion

Tank
```

Calculate

```
distance from the explosion to the NEAREST PART of the tank
(body rectangle or barrel; 0 if inside)

↓

Damage = shell damage * (1 - distance / blast_radius)     (0 beyond the radius)

↓

Tank Health
```

Example

```
Damage

100%   explosion inside the tank

80%

60%

40%

10%

0%     at or beyond the blast radius
```

The closer to the centre of the explosion, the higher the damage. Every tank inside the
blast takes damage, including the shooter's.

*(The original plan measured from the tank's ground point. That made shells that
legitimately hit the padded hitbox deal zero damage, which was fixed in `34b0c09`.)*

Each hit is also reported to the clients as a "damage event" so they can show the floating
**-N HP** number and flash the tank.

# Fuel Cans

Added after the original plan (`v9`).

```
Match start        2 cans on the map
End of every turn  +1 can, up to a maximum of 3
Spawn rule         random x; not within 80 px of a tank or another can; 40 px edge margin
Collect            a tank that drives over a can gets +40 fuel (capped at 100)
Position           only the x is stored; y follows the terrain, so craters can't strand a can
```

# Match Statistics

Added after the original plan (`v10`).

```
fire            -> MatchRecorder.start_shot(player, ammo, angle, power)
explosion       -> MatchRecorder.finish_shot(damage each tank took)
match over      -> MatchRecorder.finish()  ->  match_stats/match_<time>.json
                -> report.build_report()   ->  match_stats/match_<time>.png  (background thread)
                -> {"type": "report"} message sends the PNG once to both clients
clients         -> report_view shows it on the end screen (Tab hides it)
```

The chart has three panels: cumulative damage over time, accuracy per player, and every
shot as power vs. angle. It is built with matplotlib's `Figure` class directly (no
`pyplot`), so it needs no window and is safe to run off the game-loop thread.

# Networking

Only the server performs calculations.

Transport: TCP, each message a 4-byte big-endian length followed by UTF-8 JSON
(`network.py`). The server ticks at 60 Hz and broadcasts a full snapshot every tick.

Clients send (every frame)

```
move          -1 / 0 / 1        (Move Left / Right)

rotate        -1 / 0 / 1

power         -1 / 0 / 1

fire          true once         (Fire)

ammo          "Light" / "Medium" / "Heavy" / null

restart       true once, after a match has ended

name          new name / null
```

Server sends

```
welcome   { player_id }                       once, on connect

state     (every tick)
              terrain            the whole height map
              tanks              position, angle, power, health, fuel, ammo, name, color
              current_player_id  Turn
              projectile         position, weight
              explosion          position, plus explosion_radius
              fuel_pickups       positions
              damage_events      recent hits (id, player, amount)
              game_over_text     Winner / Draw

report    { png }                             once, when the match chart is ready
```

The server never draws anything; the clients never decide anything.

# State Machine

The server does not use an explicit enum; the state is carried by a few fields
(`active_projectile`, `acted_this_turn`, `was_moving`, `game_over_text`).

```
Waiting for Player           (server waits until both clients have connected)

↓

Player Choosing

↓

Player Moves                 (fuel is spent, cans collected)

↓

End Turn                     (movement key released; a fuel can may spawn)

OR

Player Fires

↓

Projectile Flying

↓

Explosion

↓

Damage

↓

Terrain Update

↓

Next Turn    -or-    Game Over  ->  save stats + build chart  ->  restart on request
```

# Game Loop

Server (60 Hz)

```
Read latest input of the current player

↓

Apply name changes

↓

Move / aim / fire     or     advance the projectile

↓

Collision

↓

Damage, terrain, fuel cans, turn / game over

↓

Broadcast state       (and the chart, once, when ready)

↓

Repeat
```

Client (60 fps)

```
Handle key events, read held keys

↓

Send input to the server

↓

Take the latest state broadcast

↓

Update effects and floating damage numbers

↓

Draw screen

↓

Repeat
```

## Design Principles

To keep the code maintainable:

* **Server is authoritative:** only the server computes physics, collisions, health, and terrain changes.
* **Clients are "dumb":** they render the received game state and send player inputs. Cosmetic effects (particles, shake, flashes) live only on the client and never affect the game.
* **Each module has one responsibility:** physics doesn't know about networking, rendering doesn't know about damage calculations, and terrain logic doesn't know about UI.
* **Represent game state as serialisable data:** positions, health, terrain, and turn information are sent over sockets as JSON. Even the end-of-match statistics are plain JSON, so they can be saved, reloaded and re-plotted later.

These held throughout: for example, adding fuel cans, damage events and the statistics
report each needed only a new field or message from the server and a new draw step on the
client, with no change to the engine modules.

## Deviations from the original plan

| Original plan | As built | Why |
| --- | --- | --- |
| Flat layout (`server.py`, `models/`, ...) | `src/tankbattle/` package | The course requires an installable package |
| Light damage 20, Heavy radius 50 | Light 30, Heavy radius 40 | Rebalanced after play-testing |
| Damage from the tank's ground point | Damage from the nearest part of the tank (body or barrel) | Shells that hit the padded hitbox could deal zero damage |
| Projectile and tank hit only on the body | Body and barrel, each with a 10 px margin | Hits felt unreliable |
| `ui/`: game_screen, hud, menu | Also `sound.py`, `effects.py`, `report_view.py` | Sound, effects and the end-screen chart |
| Server sends positions, terrain, health, turn, winner | Also fuel, fuel cans, damage events, explosion radius, and a one-off `report` message | Features added after the plan |
| Explicit state machine | Implicit, carried by a few server fields | Simpler for a two-player turn game |
| Sprites in `assets/` | Shapes drawn in code, sounds synthesized | No asset files needed; folders kept as placeholders |

## Ideas not yet built

The original plan suggested wind, AI opponents and further ammunition types. These are
still open, and the architecture supports them: wind would be one extra term in
`physics.step`, a new shell is one more `Ammo` subclass, and an AI opponent could be a
client that sends the same input messages.
